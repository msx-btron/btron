0. Scope & Design Invariants
----------------------------

ClockworkPi PicoCalc is a Tier-1 Embedded MCU pocket computer with:
  - CPU (Default): Raspberry Pi Pico 1 — RP2040, Dual Cortex-M0+ (ARMv6-M),
    125 MHz, 264 KiB SRAM, 2 MiB XIP Flash.
  - CPU (Option):  Raspberry Pi Pico 2 — RP2350, Dual Cortex-M33 (ARMv8-M
    Mainline + FPv5-SP FPU), 150 MHz, 520 KiB SRAM, 4 MiB XIP Flash
    (PICO_BOARD=rp2350).
  - Display:       4.0" 320x320 IPS TFT, Sitronix ST7365P on SPI1 (25 MHz).
  - Input / PMU:   QWERTY keyboard + AXP2101 PMU via STM32 on I2C1 (0x1F).

Five hard invariants govern the PicoCalc UI architecture:

  I1. Zero overlapping desktop windows. A 320x320 keyboard-driven pocket
      screen has no mouse and cannot pay for z-ordered window backing stores.
  I2. Zero pixel coordinates in applications. Every app declares widgets only;
      SegUI's resolve_segments() and resolve_body() compute all geometry.
  I3. Zero post-boot malloc(). All apps, forms, menus, dialogs, and display
      strip buffers live in static BSS/DATA checked at link time.
  I4. Banded 320x16 RGB565 rendering (20 KiB double-buffered SRAM) is unified
      across both RP2350 and RP2040 so the same UI binary model runs on both
      chips with >450 KiB (RP2350) / >200 KiB (RP2040) SRAM headroom.
  I5. Strict core layering: core_pico.c is the pure non-UI Cortex-M RTOS core
      (verified in QEMU via `make run-pico` / `make test-pico`); core_segui.c
      layers the 320x320 Palm/SegUI hardware shell on top (analogous to
      core_arm64.c on Pi 400).


1. Why Palm OS 5 HiRes (320x320) + SegUI Autolayout
---------------------------------------------------

Palm OS 5 HiRes (Tungsten / Treo) solved the exact 320x320 pocket-computer
problem with four primitives:

  1) Home Launcher      — one icon grid that launches any installed app.
  2) Single Active Form — one full-screen app owns the body segment at a time.
  3) Pull-Down Menu Bar — hidden until invoked (0 px vertical cost at rest).
  4) Modal Alert Dialog — transient confirmation / status box over the form.

B-System's existing SegUI toolkit (src/desktop/industrial/segui/segui.c)
already separates device geometry (SEGUI_PROFILE) from layout arithmetic
(resolve_segments / resolve_body) and widget painting:

  +------------------------------------------------------------------+
  | SEG_STATUS   20 px   [App Title Pill]     12:04  BAT 86%  BL 80% |
  +------------------------------------------------------------------+
  | SEG_TABBAR    0 px   (auto-hidden when active app has 1 Form;    |
  |              22 px    auto-shown when app declares >1 Forms)     |
  +------------------------------------------------------------------+
  |                                                                  |
  | SEG_BODY    276 px   stretch = TRUE                              |
  |                      (or 254 px when SEG_TABBAR is visible)      |
  |                                                                  |
  |   * Launcher:   6 SEGUI_W_BUTTON tiles -> auto 3x2 grid          |
  |   * List apps:  1 SEGUI_W_LIST -> auto full-body scrolling list  |
  |   * Text apps:  1 SEGUI_W_TEXT -> auto full-body console/editor  |
  |   * 3D app:     1 SEGUI_W_CANVAS -> auto full-body banded canvas |
  |                                                                  |
  +------------------------------------------------------------------+
  | SEG_SOFTKEY  24 px   [F1 Home]   [F2 Menu]   [Enter OK]   [Esc]  |
  +------------------------------------------------------------------+
                         Total = 20 + 0 + 276 + 24 = 320 px exact.

When `F2` (Menu) is pressed, a 1-column SEGUI_ROW dropdown overlays the top
of SEG_BODY (auto-sized via segui_row_h()). When a modal alert is active, an
auto-centered framed dialog overlays L->body. Neither reserves permanent
screen height.


2. Clean-Slate Coordinate-Free SegUI Core Redesign
--------------------------------------------------

Legacy demo files (`segui_demo.c`, `segui_phone.c` — Contacts/Phone demos)
are REMOVED and fully replaced by the Palm OS-like SegUI system. No
backwards compatibility with legacy demo layouts is required; `segui.h` /
`segui.c` are streamlined directly around the 320x320 PicoCalc Palm Form
model (while preserving coordinate-free autolayout for any screen size), and
`tools/capture_segui.c` (`make segui-screens`) is updated to render the new
320x320 PicoCalc screens.

Three core capabilities anchor the redesigned `segui.h` / `segui.c`:

2.1 New Profile: segui_profile_picocalc (320x320)
  - form_w = 320, form_h = 320; exact auto-match in segui_profile_for(320,320)
  - bands: SEG_STATUS(20), SEG_TABBAR(22, auto-skipped if n_tab <= 1),
           SEG_BODY(0, stretch=TRUE), SEG_SOFTKEY(24)
  - grid metrics: margin=4, pad=6, gap=6, btn_h=72, row_h=22,
                  min_col_w=68, max_cols=4
    -> On 320x320: body_w = 320 - 2*(4+6) = 300 px.
       4 columns = (300 - 3*6) / 4 = 70 px >= min_col_w(68).
       8 Launcher tiles automatically arrange as a balanced 4x2 grid
       (2 rows x 72 px + 6 px gap = 150 px, centered cleanly in 276 px).

2.2 New Container Widget: SEGUI_W_TEXT
  - Added to is_container() alongside SEGUI_W_LIST and SEGUI_W_CHAT.
  - resolve_body() automatically assigns it the full remaining L->body below
    any top SEGUI_W_LABEL.
  - Backed by a caller-owned static ring/line buffer (zero heap):
      * Read-only / append mode: powers Terminal (scrollback + prompt line)
        and Browser (wrapped hypertext/TAD document view).
      * Editable mode: powers Editor (cursor row/col, insert, backspace,
        newline, vertical auto-scroll).

2.3 New Container Widget: SEGUI_W_CANVAS
  - Added to is_container() alongside SEGUI_W_LIST / SEGUI_W_CHAT / SEGUI_W_TEXT.
  - resolve_body() assigns it the full remaining L->body RECT.
  - Calls a registered band-aware paint callback:
      void (*draw_band)(SEGUI_APP *app, GDEV *dev, const RECT *bounds);
    where dev->clip is the active 320x16 strip. Used exclusively by GLGears
    so 3D rasterization fits inside the same 20 KiB display strip + 10 KiB
    banded 16-bit Z-buffer with zero full-frame allocation.


3. Palm OS Application Runtime (segui_palm.h / segui_palm.c)
------------------------------------------------------------

Every PicoCalc application is a static, read-only descriptor in Flash:

  typedef struct SEGUI_PALM_MENU_ITEM {
      const char *label;
      void (*action)(SEGUI_APP *app);
  } SEGUI_PALM_MENU_ITEM;

  typedef struct SEGUI_PALM_APP {
      const char *id;                  /* "terminal", "editor", ...        */
      const char *title;               /* Launcher tile & status title     */
      SEGUI_ICON  icon;                /* Built-in SegUI vector glyph      */
      void (*build)(SEGUI_APP *app, const SEGUI_PROFILE *prof);
      BOOL (*on_key)(SEGUI_APP *app, int key);
      void (*on_tick)(SEGUI_APP *app, uint32_t now_ms);
      void (*on_close)(SEGUI_APP *app);
      const SEGUI_PALM_MENU_ITEM *menu;
      int n_menu;
  } SEGUI_PALM_APP;

3.1 Application Switch (Palm SysUIAppSwitch Equivalent)
  A single static `SEGUI_APP g_palm_app` exists in SRAM. Switching apps:
    1) Dismisses any open menu/alert overlay.
    2) Calls `cur_app->on_close(&g_palm_app)` if non-NULL.
    3) Resets `g_palm_app` and invokes `next_app->build(&g_palm_app, prof)`.
    4) Runs `segui_layout(&g_palm_app, &g_dev)` and marks all bands dirty.
  RAM cost does NOT grow with the number of installed apps.

3.2 Deterministic Event Loop (Palm AppEventLoop Equivalent)
  On every key event from I2C1 (0x1F) or UART0 mirror:
    1) F1 (Home):     Switch to Launcher (no-op if already on Launcher).
    2) Modal Alert:   If open, consumes Enter (confirm) / Esc (cancel).
    3) F2 (Menu):     Toggles pull-down menu overlay for current app.
    4) Menu Open:     Consumes Up/Down/Enter/Esc; executes item->action().
    5) app->on_key(): App-specific typing/command/scroll handling.
    6) segui_key():   Default SegUI autolayout focus/scroll/activate.

5. Banded 320x16 RGB565 Display Pipeline (dp_pico.c + st7365p_spi.c)
--------------------------------------------------------------------

Why banded rendering:
  - 320x320x32-bpp ARGB = 409,600 B (exceeds RP2040 264 KiB SRAM).
  - 320x320x16-bpp RGB565 = 204,800 B (leaves <60 KiB on RP2040).
  - 2 x (320x16x2 B) ping-pong strips = **20,480 B (20 KiB)** total SRAM!

Per-frame / dirty-band loop:
  For each dirty band b in 0..19 (y = b*16 .. b*16+15):
    1) Set GDEV clip = { 0, y, 320, y+16 }, target = strip_buf[b & 1].
    2) Run segui_paint(&g_palm_app, &g_dev) (+ menu/alert overlay if open).
       Primitives outside [y, y+16) are rejected in O(1); inside pixels are
       converted 0xAARRGGBB -> big-endian RGB565 directly into strip_buf.
    3) Wait for prior SPI1 DMA completion, issue ST7365P CASET(0..319) +
       RASET(y..y+15) + RAMWR(0x2C), start DMA Channel 0 -> SPI1 TX FIFO.
    4) Immediately compute band b+1 into strip_buf[(b+1) & 1].

Timing @ 25 MHz SPI1 (RGB565):
  - Single 320x16 band = 10,240 B = 81,920 bits -> ~3.3 ms.
  - Full 320x320 frame (20 bands) -> ~65 ms (~15 FPS; ~25 FPS @ 40 MHz).
  - Partial keystroke/focus redraw (1–2 bands) -> 3.3–6.6 ms.
  - Compile-time fallback PICOCALC_LCD_RGB666=1 converts strip pixels to
    3-byte RGB666 (`COLMOD 0x66`) if any panel revision requires it.

The 25 MHz line above is the original proposal. The linked RP2040 images
program SPI1 at 31.25 MHz and do not raise it. Section 11 is the band
budget those images use. A lower render size does not multiply that
budget by the pixel ratio.


6. Keyboard & Southbridge Input Map (i2ckbd_stm32.c)
----------------------------------------------------

I2C1 (GP6 SDA, GP7 SCL, pull-ups enabled, 10 kHz, addr 0x1F):
  - Poll REG_ID_FIF (0x09) at 20–50 Hz (16-bit word: lo=state, hi=code).
  - State 1 = key press, 2 = hold/ctrl-down (0x7E02), 3 = release (0x7E03).

  STM32 Code   Physical Key    Palm/SegUI Action
  ----------   ------------    -----------------------------------------
  0xB5         Arrow Up        Move focus / scroll up / GLGears pitch
  0xB6         Arrow Down      Move focus / scroll down / GLGears pitch
  0xB4         Arrow Left      Prev col / Prefs dec / GLGears yaw
  0xB7         Arrow Right     Next col / Prefs inc / GLGears yaw
  0x0A / 0x0D  Enter           Activate / Open / Confirm alert
  0x08 / 0x7F  Backspace       Delete char / Browser Back
  0x09         Tab             Cycle focus / next tab
  0x1B         Esc             Close menu/alert / Back
  0x81 (F1)    F1              Palm HOME (switch to Launcher)
  0x82 (F2)    F2              Palm MENU (toggle app dropdown menu)
  0x20..0x7E   ASCII           Direct text input (Terminal/Editor/Search)

  GP10-12, LCD CS/DC/RST GP13-15) before peripheral traffic begins.


8. Battery & Power-Efficiency Architecture
------------------------------------------

PicoCalc runs on dual 18650 cells; every subsystem must earn its milliwatts:

  P1. Event-Driven WFI Idle Sleep:
      No `while(1)` busy-wait loops anywhere in kernel or UI. Idle task
      executes `wfi`; Core 1 remains parked in bootrom/deep `wfe` (saves
      ~30-40% core dynamic power).
  P2. Demand-Driven Dirty-Band Rendering (0 FPS When Static):
      A 20-bit `dirty_bands` mask tracks modified 320x16 strips. When
      `dirty_bands == 0` (idle Launcher, Terminal, Editor, Browser, Cabinet,
      Preferences), 0 SPI1 clocks and 0 DMA bursts occur. Only GLGears runs
      continuously (and pauses on Space or inactivity timeout).
  P3. Smart Backlight & ST7365P Sleep:
      - Keyboard backlight (STM32 0x0A) defaults to 0 (OFF) at boot.
      - Configurable inactivity timer (Preferences): 60 s -> dim LCD
        backlight (0x05) to 20%; 5 min -> ST7365P DISPOFF (0x28) + SLPIN
        (0x10) + backlight 0; any key wakes via SLPOUT (0x11) + DISPON (0x29).
  P4. Adaptive I2C1 Polling Cadence:
      Poll STM32 REG_ID_FIF (0x09) at 50 Hz (20 ms) while active, stepping
      down to 10 Hz (100 ms) after 3 s idle. Poll REG_ID_BAT (0x0B) once
      every 15 s (never per frame).
  P5. Peripheral Clock & Reset Gating:
      Keep unused peripherals held in RESETS (ADC, PWM, PIO, SPI0 when SD
      idle, I2C0, UART1, USBCTRL, HSTX, TRNG). Only un-reset IO_BANK0,
      PADS_BANK0, UART0, SPI1, I2C1, DMA, TIMER0.
  P6. Minimal, Spec-Driven Code Discipline:
      All Pico/SegUI sources compile with `-Os -ffunction-sections
      -fdata-sections -Wl,--gc-sections -Wall -Wextra -Werror`. Every
      register offset, bitfield, and init sequence cites its hardware spec
      (RP2350 DS, RP2040 DS, ST7365P V1.0, STM32 i2ckbd, ARMv8-M/v6-M ARM).


9. Silicon Bring-Up Safeguards & Gap Analysis
---------------------------------------------

Six real-hardware failure modes explicitly mitigated by design:

  G1. RP2350 TICKS Generator (0x40108000):
      Unlike RP2040 (WATCHDOG_TICK), RP2350 gates TIMER0 and PROC0 SysTick
      ref clocks via the dedicated TICKS peripheral. hal_rp2xxx.c MUST
      program TICKS_TIMER0_CYCLES=12, TICKS_TIMER0_CTRL=1 (1 MHz) and
      TICKS_PROC0_CTRL=1 before enabling SysTick or delays.
  G2. RP2350 Pad Isolation (PADS_BANK0 bit 8 ISO=1):
      RP2350 resets all GPIO pads isolated. hal_rp2xxx.c MUST clear ISO=0
      on every configured pin (GP0/1, GP6/7, GP10-15) before I/O.
  G3. I2C1 Stuck-Low SDA Recovery:
      If MCU resets mid-I2C transaction, STM32 can hold GP6 (SDA) LOW.
      i2ckbd_init() checks GP6; if LOW, bit-bangs 9 SCL pulses on GP7 +
      STOP condition before switching GP6/GP7 to I2C1 function.
  G4. HardFault Diagnostics on Real Silicon:
      HardFault_Handler dumps PC/LR/PSR/CFSR/HFSR to UART0 AND draws a
      minimal raw-SPI1 (blocking, no DMA/RTOS) red fault banner on ST7365P.
  G5. SD-Boot (+200 KiB) Relocated Handoff:
      When launched by pico_multi_booter at 0x10032000, Reset_Handler runs
      `cpsid i`, explicitly writes SCB->VTOR = __vectors_start__, and
      resets SPI1/I2C1/DMA so no stale bootloader IRQ or DMA channel fires.
  G6. Clean Legacy Removal Blast Radius:
      Verified grep across repo: only Makefile (CAPTURE_SEGUI_SRCS),
      include/btron/segui.h, tools/capture_segui.c, and
      scripts/screen_update_segui.py reference segui_demo/segui_phone.
      All four will be updated atomically when removing the legacy files.

11. PicoGL band budget and Pico Quake resolutions
-------------------------------------------------

This section is the PicoGL specification. doc/md/PICOGL.md was removed
when this section landed.
CLK_SYS stays 125 MHz. SPI1 stays 31.25 MHz. DMA channel 0 has one owner,
core 0. SegUI stays on both images. A full 320x320 RGB565 framebuffer
(204800 bytes) plus a matching int32 depth picture does not fit beside
the shell, so color is two 320x16 strips (20480 bytes) and depth for a

11.3 Wire term, fixed for a full panel

One 320x16 RGB565 band is 10240 bytes, 81920 bits.

  band_ms  = 81920 / 31.25e6 * 1000 = 2.621 ms
  panel_ms(Dw, Dh) = Dw * Dh * 16 / 31250
  panel_ms(320, 320) = 52.43 ms

Twenty bands are the whole panel. If the CPU finishes a band while the
previous band is on the wire, the frame is the panel time. 1000/52.43
is 19.1 FPS. core_segui also waits about 1 ms once per frame, so a CPU
that hides completely lands near 18.7 FPS, not 20 and not 30. The old
section 5 figure of ~15 FPS is the same panel at the proposed 25 MHz
(65.5 ms). That clock is not what the images program.

A window presents fewer bands. The animated body mask 0x0007FFFC is 17
bands, 17 * 2.621 = 44.6 ms, about 22 FPS if the CPU is hidden. The
panel term depends on the destination that is actually sent. It does
not depend on r_mode.

11.4 CPU term, not linear in area

The user measured 320x320 at 4 FPS on 2026-11-22 after the band-clipped
edge walk (it had been 1-2 FPS). 4 FPS is about 250 ms of CPU. The 52 ms
panel transfer sits inside that, so the frame is CPU-bound. Nothing in
this section is a new measurement. The split below is that one 250 ms
budget, not three stopwatches:

  T_fixed ≈ 10 ms   BSP walk, capture, the nearer-first sort, HUD
  T_edge  ≈ 20 ms   edge setup. About 1 ms per 16-row band at 320 tall,
                    because each overlapping triangle does three software
                    divides once per band it touches. Scales with height.
  T_pix   ≈ 220 ms  z-tested pixel writes, including overdraw. Scales
                    with area. This is the 4 FPS term.

  cpu_ms(Rw, Rh) = 10
                 + 20 * (Rh / 320)
                 + 220 * (Rw * Rh) / (320 * 320)

  frame_ms = max(panel_ms(Dw, Dh), cpu_ms(Rw, Rh)) + 1
  fps      = 1000 / frame_ms

Only the pixel term divides by the area ratio. The edge term divides by
the height ratio. The fixed term does not move. The panel term does not
move while the picture still stretch-fills 320x320. So:

  320x320 at 19 FPS  is not  160x160 at 76 FPS.

19.1 * (320*320)/(160*160) = 76.4, which is the "80 FPS" reading. It
treats the wire as if a smaller render sent fewer panel pixels. The
160x160 picture is scaled back up to 320x320, so the wire stays 52.43 ms.
The same reading also ignores T_edge and T_fixed. A pure pixel law on
the measured 4 FPS would be 4 / 0.25 = 16 FPS at 160x160, still not 80,
and still high because it drops the edge and fixed terms.

That split is retired. It charged the edge divide to render height.
The divide was charged again on every destination band, and fullscreen
is 20 bands at every r_mode. Section 11.5 replaces it with the flat
200 ms reading and the rate derived from paying that init once.

11.5 Fullscreen timings

Panel term held at 52.43 ms.

  frame_ms = max(52.43, cpu_ms) + 1
  derived  = 1000 / frame_ms

The measured column is the user's pill on the image that still divided
each edge on every destination band: about 5 FPS, about 200 ms, at
every size. 320x320 had been 4 FPS before that. The derived column is
this link. It has not been read off the pill.

At most 30 ms of the 200 ms can scale with the picture and still hide
inside one step of a pill that read 5 at both 320x320 and 80x80. The
other 170 ms was the edge init, paid once per destination band. Twenty
bands is 8.5 ms a band. This link pays that init once. The 30 ms is
split into a height term and an area term:

  cpu_ms(Rw, Rh) = 8.5
                 + 15 * (Rh / 320)
                 + 15 * (Rw * Rh) / (320 * 320)

8.5 + 15 + 15 = 38.5 ms at 320x320. At 80x80 the same formula is
8.5 + 3.75 + 0.94 = 13.2 ms. The 25 ms gap fits in the step that read
5 for both. The one-bit divider makes the 8.5 ms smaller and is not
given a further factor. A cpu_ms already under 52.43 cannot derive
above the wire ceiling.

  size       area    cpu ms   frame ms   derived   measured   pure area   wire*area
  320x320    1.00     38.5      53.4       18.7      5           4.0         19
  160x320    0.50     31.0      53.4       18.7      5           8.0         38
  320x160    0.50     23.5      53.4       18.7      5           8.0         38
  160x160    0.25     19.8      53.4       18.7      5          16.0         76
  128x128    0.16     16.9      53.4       18.7      5          25.0        119
  128x96     0.12     14.8      53.4       18.7      5          33.3        159
  80x80      0.0625   13.2      53.4       18.7      5          64.0        306

Every derived rate is 18.7 because every cpu_ms is under the panel.
18.7 is 1000/53.4, the fullscreen ceiling with the 1 ms delay. It is
not a pill reading. pure area = 4 / (Rw*Rh/320/320) and
wire*area = 19.1 / (Rw*Rh/320/320) are the linear laws this panel does
not follow. A window of about 17 bands is 44.6 ms. The same cpu_ms then
derives near 22 when the CPU is under that window. A pill well under
18.7 at fullscreen 320x320 means a large share of the 200 ms was once
per frame, projection and the BSP, rather than the per-band edge init.

11.6 15 FPS at a real 320x320

15 FPS is a 66.7 ms frame. The panel already costs 52.4 ms, so the CPU
term has to land at or under about 66 ms. The render size stays 320x320.
This is not a smaller picture scaled up, and fullscreen is the check that
holds the panel term fixed.

The Quake image arms coverage only after the nearer-first sort. The
span then does four things the per-pixel cover walk did not:

  - Flat iz is the sort key, and a tie keeps the earlier triangle, which
    is the same rule as a strict greater-than test. The cover path does
    not load or store iz. A later triangle cannot win a pixel an earlier
    one wrote.
  - A 32-pixel word that is already full is one compare. A word that is
    entirely free is halfword stores. Only a word that is partly full
    walks bits. The second scan that used to reject a span before that
    walk is gone.
  - The band is not cleared to sky first. After the triangles, one sky
    span fills the bits that are still clear, so a covered pixel is
    written once.

The edge divide is the software floor divide. A device build that fed
the SIO unsigned divider read DIV_QUOTIENT on the next instruction.
That register is undefined until 8 cycles after the divisor write, so
the edge positions were garbage. The repair loop then ran out its 48
steps on every row and divided again into the same register. The picture
tore, and every r_mode landed near 5 FPS because that loop does not
shrink with the render size. The span does not touch the SIO divider.
After that divide was put back, the user measured the geometry fixed
and the pill still near 5 FPS at every r_mode, including the small
ones. 320x320 had moved from 4 FPS to about 5. Section 11.5 records
that reading. The remaining cost does not scale with area.

Fullscreen still paints about 20 destination bands. A scaled r_mode
calls the span on each source slice, and a triangle that covers the
view overlaps every slice, so edge_init ran about 20 times per such
triangle at 80x80 and at 320x320. The old software divider shifted by
a variable count. On this M0+ a variable shift costs a cycle per bit,
so one 32-bit divide was on the order of a thousand cycles. Projection
used the same 64-bit divide. Pixel loops shrink with r_mode. That
setup did not.

This link keeps the edge algebra and steps a saved remainder. The first
band a triangle touches divides. Later bands reuse q and r when the
next ymin is the row those remainders were left for, and edge_advance
walks the rest. A gap re-divides. Horizontal edges still recompute.
The divider shifts one bit at a time. cw_project uses a 32-bit divide
when the already-rounded numerator and the denominator fit in a signed
32-bit value. cw_lerp is unchanged. The SIO divider stays unused. Quake
spans stay on core 0. There is no second 320 framebuffer. Clocks are
unchanged. The resume tables are 896*3*2 ints plus 896 int16s, 23296
bytes, cleared after the nearer-first sort. Gears do not call
picogl_set_edge_resume.

RP2350-Quake and frank-quake2 each build a polygon's edges once and
then fill a framebuffer this SRAM cannot hold. frank-quake2 is Quake
II on an RP2350 at 504 MHz with 8 MB of PSRAM, a 320x240 8-bit picture
doubled onto HDMI, and the two cores splitting the world and the edges.
Its demo1 time is not a measurement of this board. RP2350-Quake keeps
an indexed picture and hands the panel to the other core. This image
keeps the order only: divide an edge once, then step it across the
bands. The picture stays the 16-line strip.

Gears never call picogl_set_cover. make test-picogl-raster paints
through paint_span_write, and one more check compares a resumed edge
with a fresh divide. Those pixels stay bit-identical. A host
comparison of the same nearer-first triangles, cover against the z-test,
matched inside the view, including each 32-pixel residue and a window
that does not start at the origin. An unsorted pair diverged, which is
what the sort invariant requires.

This link does not claim 15 FPS. Section 11.5 derives 18.7 for every
fullscreen size because the CPU term falls under the 52.4 ms panel.
That 18.7 is the wire ceiling, not a pill reading. The recorded device
rates are the user's: 4 FPS at 320x320, then about 5 FPS at every r_mode on
the torn SIO image, then geometry fixed and still about 5 FPS at every
r_mode after the software divide returned. Flash
btron-picocalc-quake-rp2040.uf2 by hand and read the pill at fullscreen
320x320 and at a small r_mode.

Core 1 is not given Quake spans. The strip is also SegUI's. A row split
would race that strip. Clocks stay where they are. A retained 320x320
color-plus-depth picture does not fit: after this link Quake has 11716
bytes free under 215040, and 320x320 RGB565 plus int32 depth is
204800 + 409600.

11.8 Pipeline

  core 0, once per frame
  1 Submit      seven R_EEGS_* calls, or the GLES door for gears
  2 Transform   one camera matrix, then an integer clip and divide
  3 Bin         gears and XMB post to the span ring; Quake captures
  core 0, each dirty band (Quake spans are not posted to core 1)
  4 Raster      edge walk, seal. Quake divides an edge on the first
                    band and steps the remainder after that. Coverage
                    skips a filled word. Otherwise a strict iz test
                    (larger iz wins)
  5 Cover       system-font menu, HUD, status bar
  6 Scan        DMA channel 0

GL_BACKEND_PICOGL = 5. The seven calls are Live, BeginFrame, SetCamera,
Poly, Tris, Fill, and String. On the device, world triangles are
picogl_world_tri with PICOGL_SEAL. Gears use picogl_screen_tri and do
not set the seal. The span walks pixel centers. A shared edge can miss
both faces; the seal covers one extra pixel on a world triangle.
cw_lerp rounds to nearest. Core 1 wakes so ps can show the picogl row.
Quake paints on core 0 because the strip is SegUI's as well.

The triangle is 24 bytes. The span ring is 128 slots, 3072 bytes, and
is not a second bin table. A full ring waits for one slot. Core 1 never
programs SPI, DMA, or GPIO.

11.9 Decisions that still hold

  - The seven R_EEGS_* calls are the scene API. PS2 keeps its own body.
  - Both images keep the eight shell apps. The center tile is the only
    difference. PALM_APP_GLGEARS is not renumbered.
  - The framebuffer is the 16-line strip.
  - Rectangles and the system font are not meshes.
  - progs.dat is not linked. The device console is the integer command
    list in start_sim.c.
  - v1 is silent.
  - The old "draw the world at 160 and store it 2x" choice is retired.
    The seven sizes in section 11.2 all stretch to the destination.
    Direct paint is only the case where render size equals destination.
  - UART lines picogl gears at 20 FPS and picogl xmb / quake at 12 FPS
    were targets in the phase plan. They were not measured. The device
    Quake rates recorded here are the user's: 4 FPS at 320x320, then
    about 5 FPS at every r_mode with the geometry fixed. This link is
    not a new measurement.
