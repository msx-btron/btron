PICO.txt — PicoCalc builder's book
=================================

B-System on the Clockwork PicoCalc. Two images, one shell, one span.
This file is the reimplementation blueprint. A number in the measured
column is a rate the user read on a board. A derived number is arithmetic
on that rate or on the panel wire. 18.7 FPS is the wire ceiling. It is
not a pill reading and not a promise.

CLK_SYS stays 125 MHz. SPI1 stays 31.25 MHz. Do not raise either.
The SIO divider stays unused. SegUI stays on both images.
PICO_BOARD defaults to rp2040. PICO_BOARD=rp2350 is the override and is
not what the sizes below were linked for.


1. The machine
--------------

  CPU     RP2040, two Cortex-M0+ at 125 MHz. No FPU. No LDREX.
          264 KiB SRAM at 0x20000000. 2 MiB XIP at 0x10000000.
          Scratch X is 4 KiB at 0x20040000. Scratch Y is the next 4 KiB.
          Each scratch bank is single-ported. Two cores that fetch from
          the same bank, or from the one XIP cache, serialize.
  Panel   ST7365P, 320x320, RGB565, SPI1, DMA channel 0.
          One owner: core 0. Core 1 does not touch SPI, DMA, or GPIO.
  Input   QWERTY plus the STM32 keyboard bridge on I2C1 address 0x1F.
  Option  RP2350 is a different chip (M33, FPU, 520 KiB, 4 MiB). The
          Quake and gears sizes in this book are the RP2040 links.
          Do not treat an RP2350 picture as this board.

SRAM gate on every picocalc link:

  __sram_used__ <= 215040
  __bss_end__   <= __stack_top__ - 4096
  __stack_top__ = 0x20040000
  __core1_stack_top__ = 0x20042000

__sram_used__ counts striped .data and .bss. It does not count scratch.
Core 0's stack is the 4 KiB under __stack_top__. Core 1's stack is all
of scratch Y. Do not put code in scratch Y.

A 320x320 RGB565 picture is 204800 bytes. A matching int32 depth picture
does not fit beside the shell. Color is two 320x16 strips, 20480 bytes,
in dp_pico.c. Depth for a Quake band is not a second picture: iz lives
on the triangle, and coverage is a bit mask.


2. The nexus
------------

One scheduler, on core 0. Core 1 is an offload engine, not a second
task list. The handoff is non-blocking and zero-copy: the consumer
reads the buffer the producer just filled. Nobody memcpy's the job
onto a second queue, and nobody waits inside the producer except the
join at the end of the frame.

M0+ has no exclusive monitor. The protocol is a single volatile flag
published last, with a data barrier on both sides.

  producer, only when go is clear
    write the payload
    dmb sy
    go = 1
    dmb sy
    sev

  consumer
    if go is clear, return
    dmb sy
    read the payload and do the work
    dmb sy
    go = 0

The payload and the flag are not the same word. Two cores must not
store adjacent halfwords in one word: SRAM has byte enables, but a
same-word store from both cores drops one of them. A timeout does not
clear go and does not reuse the buffer. The late finisher is adopted
on the next acquire, after a barrier.

Core 1's entry is cpsid i, then the job, then wfe when the job and the
span ring are both idle. It never reaps itself. It never uses the SIO
divider. The SIO base is 0xd0000000. A correct SIO sequence is a few
milliseconds and is not the floor; a sequence that reads DIV_QUOTIENT
on the instruction after the divisor write is undefined for 8 cycles
and tore the picture. Leave it out.

What runs where:

  core 0, always
    keys, the pose, the doors, the tick
    the strip, SPI, DMA, GPIO, the system font
    the Quake paint of the list that is already built
    the join, after the last band and before the next tick

  core 1, Quake image
    the next list only: BSP, project, capture, sort
    into the slot core 0 is not painting
    nothing else

  core 1, gears / XMB image
    the 128-slot span ring (24-byte triangles, 3072 bytes)
    the producer waits for one slot
    the tail moves after the paint, so the slot is the buffer

Quake does not post world triangles onto that ring. The ring stays in
the span for gears and XMB. Gears do not build a Quake list. The Quake
hook is picogl_core1_extra. In the gears image that symbol is the weak
empty body in picogl_span.c. In the Quake image start_sim.c defines it
strong. A prototype in the header marked weak would make the strong
definition weak. The prototype stays out of the header.

Optimal offload is the split above, and not a second painter. Painting
the far half on core 1 was tried. It wrote an empty band, so it could
not see the near coverage, and both cores fetched the painter through
one XIP cache. The pill did not move past a flat 10. The build is the
work that does not touch the panel, so it can overlap the paint.
The paint stays on core 0 because the strip is also SegUI's.


3. The Quake frame
------------------

Two slots, s_cap_tri[2][896]. A triangle is 24 bytes. Paint reads
s_paint. The build writes s_paint ^ 1. Slot width and height travel
with the slot. The destination s_dw, s_dh is the window, or 320x320
when fullscreen.

  cold, core 1 up
    core 0 builds slot 0 and paints it
    core 0 kicks slot 1
    later frames paint the finished slot and kick the other
    the picture is one pose behind the tick

  core 1 down
    every frame builds slot 0 on core 0
    no extra pose

  go still set at acquire
    keep painting the old slot
    do not kick, do not call picogl_begin_frame

  join, inside the present, after the last band
    spin while go, timeout 200000 us on TIMER0
    on timeout leave go set and leave the kick armed
    on success, barrier, mark the build done, clear the kick

  tick
    if go is set, return before the pose and the doors
    the present still runs; segui_palm_tick already decided the app
    is moving

Acquire arms cull and depth once. It calls picogl_begin_frame only when
go is clear, and that call zeros the span counter. The build uses
picogl_begin_capture, which must not zero that counter. The first paint
band of a frame arms coverage and the edge remainder, on core 0.
The row step is not stored. A later band divides that edge again.
The remainder still carries across the rows of one band.

UART, after the join, inside the pill window:

  ren   build, milliseconds
  ras   paint walk
  wai   join after the bands

The pill itself is wall time from one present to the next, so it also
holds the 1 ms pico_tsk_delay, the key poll, and the tick. The in-frame
number is that same window: 250000 us or 30 frames, frames * 1000 / ms,
capped at 999. Fullscreen draws it on the picture. It does not rewrite
the Palm title and does not dirty the title bands for a caption the
paint will not draw.


4. The raster contract
----------------------

Sort by descending flat iz. iz is the max of the three vertices, and
each vertex iz is at least 1. A tie keeps the earlier triangle. Strict
greater-than is the same rule: a later triangle cannot win a pixel an
earlier one wrote.

Coverage is opt-in (picogl_set_cover), armed on core 0 before the first
band, including when the list is shorter than 2. Gears never call it.
When it is armed the band is not cleared to sky or iz first.

  a full 32-pixel word is one compare
  a free word is halfword stores
  a mixed word walks bits
  do not uint32-alias the uint16 row
  the lift path does not set coverage bits
  after the list, one sky span fills the holes if any bit is still clear

A counter that hits zero early leaves a hole. The full-band stop
(s_cov_left <= 0) does not fire on drone1m1: the sky leaves a hole, so
every overlapping triangle is still entered. That is why an open
corridor costs more than a tight one, and why a smaller r_mode did not
buy a faster pill while the destination stayed the full panel.

Edges: floor_div_pos is the software divide,

  n >= 0 ? n / d : -((d - 1 - n) / d)

Vertices are clamped to +/-4096. The first band a triangle touches
divides. Later bands reuse q and r when the next ymin is the row those
remainders were left for. A gap divides again. Horizontal edges
recompute. The stored per-row quotient was dropped so the second
triangle list would fit. dr of 0xFFFF means "does not fit, divide
again" only when the step pointers are non-null. Quake passes null
step pointers.

paint_one_row calls paint_span_write and edge_init only. The cover
walk sits in the band painter. The three hot leaves live in scratch X
so the inner loop does not fetch them from XIP:

  paint_span_cover, paint_span_lift, paint_span_write

paint_tri_target does not. On the pipeline link it is 2384 bytes
(0x950) at 0x10009568, with a 352-byte frame. Scratch X had 2776 bytes
free after the three leaves (1320 used of 4096). 2384 fits, with a few
hundred bytes of margin. Only core 0 calls it now, so it would not
share that bank with core 1. It was not moved in the overlay image:
this image's question is the chrome, and a second change would mix the
reading. The builder stays in XIP on purpose. start_sim_render is
3432 bytes and does not fit in the leftover scratch. If the painter
moves to scratch X later, the builder must stay in flash so the two
cores fetch from different buses.

World triangles set PICOGL_SEAL. cw_lerp rounds to nearest. The span
walks pixel centers. A shared edge can miss both faces; the seal covers
one extra pixel. Gears use picogl_screen_tri with s_from_world clear,
so the seal stays off. Do not switch Quake to TinyGL.

Flags: FLAT 1, TEX 2, LIFT 4, SEAL 8.
PICOGL_Q10 is 1024. A band is 16 rows. The panel is 20 bands.

Direct paint is only the case where the slot's width and height equal
the destination. Every other size is stretch-filled. There is no
letterbox. The frustum aspect is the destination aspect, set on the
device with picogl_set_display(s_dw, s_dh) immediately before the
camera. The viewport stays the render size. Gears and the host tests
leave the aspect on the viewport. A square panel is aspect 1.

Budgets: TRI_ACTOR 180, TRI_SUB 220, TRI_WORLD 480, CAP_TRI 896.
Do not grow CAP_TRI. Cooked e1m1: verts 7358, faces 5516, nodes 2750,
clips 5408, doors 14. The drone track is 513 poses, 17067 ms.
Lights are baked: level = clamp(0.18 + stat/255*0.6, 0, 1), cook
"lights 198 shaded 4563 fullbright 953". Do not retune and do not recook.
The device BSP and the console are integer. Soft-float left on a device
frame is the camera matrix (once per build, on core 1), angles() once,
and the drone pose lerp on core 0 before present. There is no progs.dat.
385 edicts at about 780 bytes do not fit beside the shell.

Menu rows, in order. Boot is row 2, drone, at 160x160.

  1 PLAY E1M1
  2 DRONE
  3 320x320
  4 160x320
  5 320x160
  6 160x160
  7 80x80
  8 128x96
  9 128x128

r_mode W H selects the same table. A single number means the square
(320, 160, 80). r_mode 128 alone is rejected. The active row is starred.
The menu, the status bar, and the console are the 8x16 system font in
destination pixels. r_mode does not scale them.

f toggles fullscreen. Tab toggles the console. In fullscreen the yellow
line above the status bar is the pill ("  9 FPS", three columns, or
"--- FPS" until the first window). The word "full" is not drawn.
The menu hint still says how to leave (F WINDOW). The console command
fullscreen still answers "full" or "window" on the console log.
The health bar stays. segui_palm_paint returns before the Palm chrome,
so the title, the softkeys, and the launcher are not painted. All 20
bands are still presented, because the picture covers the bands the
chrome used to own. Windowed mode presents the body mask 0x0007FFFC
(17 bands) and, when the title number changes, bands 0 and 1.

Keys, device Quake: arrows walk and turn, q and z look, WASD walks,
space and the fire key shoot. f is fullscreen, not fire. The host gate
still treats f as fire.


5. The wire
-----------

One 320x16 RGB565 band is 10240 bytes, 81920 bits.

  band_ms            = 81920 / 31.25e6 * 1000 = 2.621 ms
  panel_ms(Dw, Dh)   = Dw * Dh * 16 / 31250
  panel_ms(320, 320) = 52.43 ms

Twenty bands are the whole panel. Paint of band N+1 overlaps DMA of
band N. If the CPU finishes each band while the previous band is on
the wire, the frame is the panel plus the last band's DMA, which is
already inside the 52.43 ms, plus the 1 ms yield. 1000/53.4 is 18.7 FPS.
That is the ceiling when the CPU hides. It is not 20 and not 30.

The old section 5 figure of about 15 FPS was this panel at a proposed
25 MHz (65.5 ms). The images do not program that clock.

A window that presents 17 bands is 17 * 2.621 = 44.6 ms on the wire,
about 22 FPS if the CPU is hidden and the title bands stay clean.
The panel term depends on the destination that is actually sent.
It does not depend on r_mode. Fullscreen sends the whole panel at
every r_mode.

  320x320 at 19.1 FPS is not 160x160 at 76 FPS.

19.1 * (320*320)/(160*160) = 76.4. That reading treats a smaller render
as if it sent fewer panel pixels. The 160x160 picture is scaled back
up, so the wire stays 52.43 ms.


6. What the board did
---------------------

Nothing in this section is a host timer. Host GLES times and host
raster checks are not RP2040 frame rates.

  image                                      drone1m1 pill
  band-clipped walk, before that             1-2 FPS at 320
  band clip                                  4 FPS at 320
  SIO divide, geometry torn                  about 5, every r_mode
  software divide restored, geometry fixed   about 5, every r_mode
  one-bit divide, edge remainder kept        9-10, every r_mode
  destination aspect, stored row step,
    full-band coverage stop                  9-10, ratio fixed
  core 1 paints the far half                 solid 10, every r_mode
  core 1 builds the next list                9-14, by corridor

The 9-14 reading is the pipeline image, during the drone1m1 flight.
The user did not publish a separate number per r_mode for that image.
The spread is the corridor. 15 FPS is 66.7 ms and is not claimed.

  pill     frame      past the 53.4 ms wire
  14       71 ms      18 ms
  9        111 ms     58 ms
  wire     53.4 ms    0, which is 18.7 FPS, not a pill

A tight corridor is the close one. An open corridor still has most of
a tenth of a second of CPU. The earlier images were flat across r_mode,
so the area term was inside one step of the pill (about 11 ms) and the
rest did not shrink with the picture. The pipeline is the first image
whose pill moves with what is on screen. Coverage can skip a filled
word. It still cannot skip a sky hole, and every triangle is still
entered on all 20 destination bands.

The table below is the resolution law those flat images already
refused, kept so a later model has the same columns. "measured" on
the rows is the resume image through the far-half image (9-10, then
10). The pipeline row is the corridor range, not a new per-size reading.
pure area = 4 / area, from the 4 FPS 320 reading. wire*area = 19.1 / area.
Neither is a pill.

  size       area    measured    pure area   wire*area
  320x320    1.00    9-14        4.0         19
  160x320    0.50    9-10..10    8.0         38
  320x160    0.50    9-10..10    8.0         38
  160x160    0.25    9-10..10    16.0        76
  128x128    0.16    9-10..10    25.0        119
  128x96     0.12    9-10..10    33.3        159
  80x80      0.0625  9-10..10    64.0        306

The retired CPU split (10 ms fixed + 20 ms of edge + 220 ms of pixels,
then a later split that charged 170 ms of a flat 200 ms to the per-band
divide) put every derived cpu_ms under the panel and printed 18.7 on
every row. The resume image removed about half of that 200 ms and
stayed above the panel. 18.7 stayed the ceiling. Do not put it back
as a predicted rate.

This overlay image has not been measured. Fullscreen already skipped
segui_paint before this image. What changed is the readout and the
bands that do not contain the status line: those bands no longer walk
the system font. The health bar is still drawn on the bands that
contain it. Compare the yellow line, same corridor, window against
fullscreen. A higher fullscreen number means the title-band Palm paint
and the off-band glyph walk were in the pill. A number that stays in
the 9-14 range means they were not, and the remaining time is the open
view. ren against ras against wai says which side is longer. If ras
leads, the paint is the pole and the build is hidden. If wai is large,
the build outlasted the paint and core 1 is the pole.


7. What is still in the way of the ceiling
------------------------------------------

In order. None of these is a promised delta.

  1. Read this image. The yellow line is the experiment. Do not add
     another change on top of an unread pill.
  2. If ras leads in an open corridor, the walk is the list entered
     on 20 bands because the sky is a hole. A sky mask that lets the
     full-band stop fire, without a counter that hits zero over a real
     pixel, is the cut that matches the 9-versus-14 spread. A wrong
     mask leaves a hole. The host raster test is the check.
  3. If wai leads, the build is the pole. The next offload is inside
     the build (a piece of the BSP or the project), not a second
     painter. Core 1 still must not touch the strip.
  4. paint_tri_target is the hot walker still fetched from XIP while
     core 1 fetches the builder from the same cache. It fits in the
     leftover scratch X, and only core 0 calls it. Moving it is a
     separate image. The three leaves are already there. The builder
     stays in flash.
  5. The per-row quotient was a real divide removed from the inner
     loop, then dropped to pay for the second triangle list. Putting
     it back means a different SRAM trade, not a quieter inner loop
     on top of this one. The edge remainder itself stays.
  6. UART is inside the pill. It is the instrument. Leave it until
     the three numbers have been read.

Rejected, and why:

  serial CPU then DMA, as the model of the old flat pill
  the SIO divider
  posting Quake spans onto the gears ring
  a row split or an x split of one frame (the edges get built twice,
    and the row count is the part that already scales)
  painting into the inactive DMA strip from core 1
  a retained 320x320 color-plus-depth picture
  both cores executing the painter from scratch X
  raising either clock
  TinyGL, a second scheduler, stripping the shell apps

References, ideas only, not copied: RP2350-Quake and frank-quake2.
Both set a polygon's edges once and then fill a framebuffer this SRAM
cannot hold. frank-quake2 is Quake II on an RP2350 at 504 MHz with
8 MB of PSRAM and HDMI. Their published rates are not measurements
of this board. Take one sentence: set the edges, then write each
pixel once. The order here is the same. The picture is the 16-line strip.

--------------------

Gate: __sram_used__ <= 215040. Scratch X is 4 KiB at 0x20040000.
Core 1 stack top is 0x20042000.

  Quake RP2040. Core 1 builds the next list. Core 0 paints.
  Fullscreen draws the pill on the frame and does not paint the Palm
  chrome. Not flashed. The 9-14 corridor reading is the previous image.
  This image's line has not been read.
    text 816580   data 2896   bss 201592

    __bss_end__ 0x20031ec8

    That nest fits in scratch Y.
    The second 896-triangle list is in. The far band (10240), the step

9. The shell
------------

Palm OS 5 HiRes is the 320x320 form. One app owns the body. There is
no overlapping window and no backing store. Widgets do not carry pixel
coordinates; resolve_segments and resolve_body do. There is no post-boot
malloc. Bands are the unit of redraw: a zero dirty mask clocks no SPI.

Profile segui_profile_picocalc: form 320x320. Status, tab (skipped when
the app has one tab), body, softkey. The launcher is one 3x3.

  1 Terminal   2 Editor    3 Browser
  4 Cabinet    5 center    6 Contacts
  7 Phone      8 Chat      9 Preferences

make picocalc: the center tile is XMB. Key 5 opens XMB. Keys 1-4 and
6-9 are PALM_APP_TERMINAL + (key - '1'). GLGears opens from the XMB
Applications row. f fills the panel for XMB and GLGears.
make picocalc-quake: the center tile is Quake. There is no XMB and no
GLGears. Key 5 stays Quake. PALM_APP_GLGEARS is not renumbered; the
Quake descriptor occupies that slot on the Quake image only.

Both images keep the eight shell apps. The center tile is the only
difference. TinyGL is on neither link. The Quake blob stays in flash
and is not copied into SRAM.

Present, dp_pico_present:

  for each dirty band
    clip = that 16-row strip
    the inactive strip is the one DMA still owns; do not paint it
    paint
    start DMA of this strip
  wait for the last DMA
  the generation counter bumps once per present

Quake renders only when the generation changes. Gears redraw when the
generation or the angle changes. Animated body frames dirty 0x0007FFFC.
A fullscreen 3D app dirties all 20 bands and the paint returns before
the Palm widgets.

Idle: the loop yields. 20 ms while typing, 100 ms after 3 s, and the
idle task sleeps in wfi. The keyboard backlight boots off. The panel
dims at 60 s and sleeps at 5 min, and a key wakes it. The battery is
polled every 15 s, not per frame. Animation skips the dim. GLGears and
the drone are animation. The menu is not, so a resolution change must
mark the panel dirty itself.

Keyboard, I2C1 at 10 kHz. The driver emits one edge, then repeats on
the Prefs delay and gap.

  0xB5 up    0xB6 down    0xB4 left    0xB7 right
  0x0A/0x0D enter    0x08/0x7F backspace    0x09 tab    0x1B esc
  0x81 F1 home    0x82 F2 menu
  On the Quake image, tab is the console and F2 returns to the menu
  from play. Esc closes the console, or leaves the app.

Boot, make picocalc-all builds four artifacts. The default make is the
RP2040 pair only when the target says so. make picocalc and
make picocalc-quake with no board flag are RP2040.

  btron-picocalc-rp2040.uf2            0x10000000  family 0xE48BFF56
  btron-picocalc-rp2040-sdboot.bin     0x10032000
  btron-picocalc-rp2350.uf2            0x10000000  family 0xE48BFF59
  btron-picocalc-rp2350-sdboot.bin     0x10032000

RP2350 pads reset with ISO set. Clear ISO on every pin the image uses
before the first peripheral transfer. RP2350 gates TIMER0 through the
TICKS block; program it before delays. If SDA is stuck low after reset,
bang nine clocks and a stop before switching the pins to I2C. A
HardFault on the device dumps to UART0 and paints a blocking red banner.
An SD-boot image sets VTOR and resets SPI, I2C, and DMA before it
trusts them.

The 64 KiB SRAM figure in older notes is the original shell estimate.
The gate that the links actually meet is section 1.


10. Decisions that still hold
-----------------------------

  The seven R_EEGS calls are the scene API. PS2 keeps its own body.
  GL_BACKEND_PICOGL is 5. On the device those calls are PicoGL.
  Gears use the GLES door (picogl_gl_*), not g_gl.
  Rectangles and the system font are not meshes.
  The cooked Quake font is compiled out of the device image.
  pak0.pak is not edited. libc_shim stays.
  v1 is silent.
  The framebuffer is the 16-line strip.
  Direct paint is only render size == destination.
  The seven stretch-filled sizes in section 4 are the menu.
  UART lines that once said gears 20, xmb 12, quake 12 were targets.
  They were not measured. The device Quake rates are section 6.
  Core 1 is a picogl row in ps, not a second scheduler.
  Between frames that row is RDY and the queue is 0. That is idle,
  not a stalled paint. OFF means the wake never landed and core 0
  paints. ERR means the wake was abandoned after three timeouts.
  QEMU mps2 is one CPU or leaves CPU1 off. It does not prove the
  RP2040 wake. make test-picogl-cores is the host stand-in.
